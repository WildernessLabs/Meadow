# Running Unit Tests

OS unit tests can be run using the `meadow developer` command.  These tests are split into user space tests and kernel tests.

## Building the Tests

The various tests are built into the system using the command `build.sh --unittests=???` where `???` represents a comma delimited list of the tests to be built.

E.g.

* `build.sh --unittests=esp`
* `build.sh --unittests=esp,cell`
* `build.sh --unittests=all`

The build script should be checked for values for the test types.

The tests can be verified using the command `meadow developer`, this will list all of the tests built into the system.  Note that `meadow developer -p 0` is equivalent to `meadow developer`.  Typical output is:

```
Setting developer parameter 0 to 0
Available tests:
    1 - sprintf_chk tests
    2 - GPIO tests
    3 - NuttX SQLLite tests
    4 - MCU Overload tests
    5 - Chat client tests
    6 - Battery backed register tests
    7 - SD card tests
    8 - Power management tests
    9 - ISO8601 tests
    10 - Quick and Misc tests
    11 - Tensorflow tests
.
.
.
```

## Running the Tests

The tests can be run using the command `meadow developer -p <test number>` where the test number can be found in the list of tests generated by the `meadow developer` command.

Some of the tests take additional parameters, for example, the ESP web resource test.  In this particular case, this is the number of times to run the test.  These parameters are passed through the `-v <some number>` parameter.

So in the case of the ESP test the command `meadow developer -p 1001 -v 10` will run ESP tests to read a web resource 10 times.

The network tests require additional parameters and these are stored in the file `network_test.config.yaml` which should be written to the root of the Meadow board.  An example file can be found in `sample_network_test.config.yaml`.  The basic structure is:

```yaml
TestParameters:
    SSID: MeadowTest
    Password: MeadowTest
    ServerIP: 192.168.1.68
    ServerPort: 80
    Resource: LargeFile1.html
```

This file when used in combination with the `meadow.config.yaml` file can be used to change the resource being read as well as the interface to be used.

## Code Structure

The tests are split into two groups:

* OS (running in kernel space)
* User space tests

The `developer_tests.c` holds a list of all of the tests (both user and kernel space) along with their descriptions.  It also holds a table of the test methods associated with each user space test.

The table of methods for the OS are held in `meadow_kt_dispatcher.c` and the tests are executed through a single method call (`meadow_kt_dispatcher`).
